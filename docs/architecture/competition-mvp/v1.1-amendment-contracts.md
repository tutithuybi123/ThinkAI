# Competition MVP v1.1 amendment — contracts and migration

`competition-demo-v1.1` extends the runtime-reviewed modular monolith. Existing challenge, transfer, receipt, persistence, API and event contracts remain the migration base; no component is replaced merely for architectural neatness.

## Grading authority and decision table

The evaluator produces evidence, the **server-side grading aggregator** combines it under this table, and the **backend policy** decides `practice_pass`, `transfer_pass`, receipt eligibility, and next action. An AI response never directly changes those states.

This table applies when a task requires written-reasoning evaluation. A task whose reviewed contract does not require a rubric may use an applicable deterministic validator alone. “Not applicable” means the reviewed task intentionally has no reliable deterministic validator for that facet; it is not a validator failure.

| Deterministic final facet | Server-semantic-validated rubric facets | Aggregate outcome | Gate consequence |
|---|---|---|---|
| correct | final correct; reasoning and all required criteria correct | `CORRECT` | eligible to satisfy the grading gate |
| correct | final correct; reasoning or a required criterion partial | `PARTIALLY_CORRECT` | no full pass; recovery feedback/attempt allowed |
| correct | final correct; reasoning or a required criterion incorrect | `PARTIALLY_CORRECT` | no full pass; recovery feedback/attempt allowed |
| correct | final incorrect or any deterministic/rubric final-facet conflict | `UNCERTAIN` | fail closed; no pass |
| correct | any required facet/criterion uncertain | `UNCERTAIN` | fail closed; no pass |
| incorrect | final incorrect; no required facet contradicts it | `INCORRECT` | no pass; recovery/another permitted attempt only |
| incorrect | final correct or other conflict | `UNCERTAIN` | fail closed as deterministic/rubric conflict; no pass |
| incorrect | any required facet/criterion uncertain | `UNCERTAIN` | fail closed; no pass |
| not applicable | final correct; reasoning and all required criteria correct | `CORRECT` | eligible to satisfy the grading gate if rubric, content version, evaluator schema, and aggregation policy are valid |
| not applicable | final/reasoning/required criteria indicate partial completion | `PARTIALLY_CORRECT` | no full pass |
| not applicable | final incorrect; required criteria support incorrect | `INCORRECT` | no pass; recovery/another permitted attempt only |
| not applicable | any required facet/criterion uncertain | `UNCERTAIN` | fail closed; no pass |
| any required evaluator route | unavailable | `UNCERTAIN` | fail closed; no pass |
| any required evaluator route | malformed | `UNCERTAIN` | fail closed; no pass |
| any required evaluator route | schema-invalid | `UNCERTAIN` | fail closed; no pass |
| any required evaluator route | semantically inconsistent facets/criteria | `UNCERTAIN` | fail closed; no pass |

`CORRECT` is the only aggregate outcome that may satisfy a Practice or Transfer grading gate. For a written-solution task with no applicable deterministic validator, valid reviewed-rubric facets can provide evidence through which the server aggregator produces `CORRECT`, sufficient for backend policy to create `practice_pass` or `transfer_pass`; this is the constrained reviewed-rubric route already contemplated by ADR-006, not evaluator policy authority. The policy additionally requires the exact approved content/evaluator/policy versions and all existing session/isolation guards.

`PARTIALLY_CORRECT` is durable explanatory evidence only: it never manufactures a full pass, transfer eligibility, receipt, or progression change. `UNCERTAIN` is also durable operational evidence where appropriate, but it is a fail-closed non-pass. Receipt eligibility requires qualifying `CORRECT` practice and `CORRECT` isolated transfer results for the bound pair, plus existing reveal/receipt policy requirements.

```ts
type GradingOutcome = "CORRECT" | "PARTIALLY_CORRECT" | "INCORRECT" | "UNCERTAIN";

interface RubricFacetEvaluation {
  // Required only when the reviewed rubric declares finalAnswerFacet: "required".
  finalAnswer?: "correct" | "incorrect" | "unknown";
  reasoning: "correct" | "incorrect" | "partial" | "not_assessed" | "uncertain";
  criteria: readonly { id: string; status: "correct" | "incorrect" | "partial" | "not_assessed" | "uncertain" }[];
  method?: string;
  errors: readonly { code: string; location?: string }[];
  confidence: "high" | "medium" | "low";
  evaluatorVersion: string;
}

interface ReviewedRubricGradingShape {
  finalAnswerFacet: "required" | "not_applicable";
  reasoningFacet: "required" | "not_applicable";
  requiredCriterionIds: readonly string[];
  optionalCriterionIds: readonly string[];
}
```

The preferred v1.1 contract is **facet evidence, not model-supplied outcome**: the evaluator never returns `GradingOutcome`; the server derives it from validated facets and the reviewed rubric's required criteria. Before derivation it must perform, in order: schema validation, criterion-ID validation, required-criterion completeness validation, then facet semantic-consistency validation.

The reviewed `ReviewedRubricGradingShape` is the sole authority for requiredness; model criteria cannot add, remove, or reclassify required criteria. Every required criterion ID must occur exactly once. A missing or duplicate required ID, any unknown ID, or a duplicate optional ID is invalid evaluator evidence and yields `UNCERTAIN`. Optional criteria may be omitted; when present, `not_assessed` is neutral diagnostic evidence and cannot manufacture either success or failure. A required criterion with `not_assessed` or `uncertain` yields `UNCERTAIN`.

When `finalAnswerFacet` is `required`, `finalAnswer` must be present; `unknown` yields `UNCERTAIN`. When it is `not_applicable`, `finalAnswer` must be omitted: written tasks without a final-answer facet use this reviewed shape, not `unknown`. In v1.1 written-reasoning tasks declare `reasoningFacet: required`; `reasoning: not_assessed` or `uncertain` then yields `UNCERTAIN`. A future task without that facet must declare `reasoningFacet: not_applicable`; it cannot silently use `not_assessed` to pass a required facet. Semantic validation also rejects, for example, a response that marks `finalAnswer: correct` while its required final-answer criterion is `incorrect`, or claims all required criteria are correct while an error contradicts one. Such invalid evidence produces `UNCERTAIN`, not a guessed verdict.

`confidence` is retained only as diagnostic/benchmark provenance. It does not upgrade or downgrade `GradingOutcome`, affect `practice_pass`, `transfer_pass`, or receipt eligibility, override semantic validation, or resolve deterministic/rubric conflict. v1.1 establishes no confidence threshold; any policy use would require calibration evidence and a separate approved decision.

Deterministic validators own numeric/tolerance/unit/set/structured-field/symbolic cases when an approved deterministic adapter exists. The rubric evaluator is invoked only after submission for a reviewed rubric and structured output. If no valid evaluator result is available, the aggregate outcome is `UNCERTAIN` rather than guessed correctness.

## AI boundary

| Contract | Input | Output | Forbidden effect |
|---|---|---|---|
| Practice Companion | practice snapshot, approved AI guidance, bounded learner message and active practice conversation | untrusted candidate learner reply and optional proposed support metadata | score, authoritative support/reveal/exposure facts, policy mutation, receipt/progression mutation, transfer material |
| Practice Rubric Evaluator | post-submit practice response, expected result, reviewed rubric, practice `referenceSolutions[]`, misconceptions, evaluator/version metadata | `RubricFacetEvaluation` schema | learner-facing pre-submit help; requiring reference method/order/wording; policy mutation |
| Transfer Rubric Evaluator | **after submission only:** transfer response, transfer expected result, transfer reviewed rubric, transfer's own non-canonical `referenceSolutions[]`, transfer misconceptions if needed, evaluator/version metadata | `RubricFacetEvaluation` schema | practice conversation/hints/answer/reference/feedback/AI state; pair connection/reveal; learner-facing pre-submit help; policy mutation |
| Practice Process Feedback | post-submit Practice grading evidence + structured Practice assistance summary + active Practice conversation when operationally retained + approved Practice/content/version metadata required for feedback | explanatory feedback schema | operate on Transfer; receive any Transfer context; change grading/policy; create pass/receipt; mutate progression |

`referenceSolutions[]` are non-canonical supporting evidence. The evaluator must not require a learner to reproduce a teacher method, sequence, or wording: a factorization reference and a mathematically valid quadratic-formula solution can both be `CORRECT`.

## Assistance provenance and retention

Reuse the event envelope and append-only ledger. The model supplies only candidate output/proposals; the server validates/classifies it and assigns `supportLevel`, `answerRevealAttempted`, and `responseBlocked`; the server then records `answerRevealed` from actual delivery outcome. Each server-created assistance event references event/correlation/conversation identity, actor/session/task/task-family/micro-skill/content/guidance versions, timestamp, provider/model/prompt version when invoked, and those facts. Client-supplied versions, levels, or exposure facts are ignored/rejected. A blocked candidate records attempted `true`, blocked `true`, revealed `false`; an unsafe response actually delivered records revealed `true` and remains append-only evidence.

Operational practice conversation context is server-side, access-controlled, minimized, and available only while needed for companion continuity and post-submit Process Feedback. Durable learning evidence keeps structured assistance facts and version provenance rather than requiring indefinite raw transcript retention. Retention duration is **TBD before production deployment**; P0 prohibits ordinary-log/raw-transfer leakage and defaults raw conversation/reasoning away from model training.

## Transfer isolation addition

Transfer cannot construct a companion request. It receives only its own task snapshot and neutral condition text. Pre-submit has no learner-facing AI assistance. No learner-facing or model contract in Transfer may receive Practice conversation, assistance summary, Process Feedback, answer/reference, hints, AI state, or pair connection/reveal.

The post-submit Transfer Rubric Evaluator may receive transfer-owned grading material only. Practice Process Feedback cannot operate on Transfer. v1.1 adds no Transfer learner-facing feedback feature. If a later version adds one, it must use a separate transfer-owned contract restricted to submitted Transfer response, Transfer grading evidence, and Transfer-owned reviewed content/version data, while preserving reveal/pair isolation. The pair relation remains server-only until a qualifying transfer result enables the authored reveal.
